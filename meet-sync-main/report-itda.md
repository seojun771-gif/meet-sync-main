# 잇다(ITDA) 검증 세션 리포트

> "우리는 팀을 매칭해주는 서비스가 아니라, 팀이 끝까지 완주하도록 신뢰를 설계하는 서비스다."

---

## 0. 작업 흐름 — 여기까지 오는 다섯 단계

기획 문서 한 장에서 시작해, 다음 단계의 입력이 이전 단계의 결과물이 되는 순서로 진행했다.

1. **계획 검증 인터뷰** (`/grill-me`) — 기획서를 읽고 8문항 + 후속 3문항으로 빈 칸을 캐물었다.
2. **명세로 정리** (`/to-spec`) — 인터뷰 답변을 합성해 [`specs/spec-itda.md`](specs/spec-itda.md)로 정리했다.
3. **티켓으로 분해** (`/to-tickets`) — 명세를 [`tickets-itda.md`](tickets-itda.md) 6조각으로 잘랐다.
4. **검증 설문 제작** — 아직 결정하지 못하고 남겨둔 가정을 [`survey-itda.md`](survey-itda.md) 16문항으로 정리했다.
5. **세션 리포트** — 1~4단계 전체를 문서 한 장으로 종합했다 (이 문서).

---

## 1. 문제와 포지셔닝

링크드인·사람인은 이미 검증된 경력을 가진 사람과 기업을 잇는 시장이고, TEAMPL 같은 팀매칭 서비스는 성향이 맞는 사람을 빠르게 찾아주는 시장이다. 잇다(ITDA)는 이 둘 사이, **"팀을 구성한 이후 실제로 완주하는 과정"**을 데이터화하는 유일한 서비스를 지향한다.

이 세션은 이 기획 문서의 논리적 빈틈을 찾기 위한 인터뷰였다 — 새 주장을 더하지 않고, 이미 쓰인 내용 중 결정이 안 된 지점만 물었다.

---

## 2. 검증 인터뷰 — 8문항 + 후속 3문항

| # | 질문 | 확정된 답 |
| - | ---- | -------- |
| 1 | 누가, 언제 쓰는가 | 공모전·조별과제·동아리 세 상황 모두 잠재 타겟. 첫 타겟은 설문 결과로 확정 |
| 2 | 지금은 어떻게 구하고 있나 | 인맥 → 에브리타임 → 카카오톡 오픈채팅 순으로 대안을 소진 |
| 3 | 뭐가 있으면 "됐다"인가 | 사용자 반응 > 발표·심사 통과 > 기술 구현 가능성 순으로 검증 |
| 4 | 뭘 만들지 않을 것인가 | Phase 2~3(외부 검증 하이브리드, 채용 연계) 제외 — MVP 범위만 |
| 5 | 가장 먼저 돌아가야 할 것 | "완주"의 정확한 정의 — 안 정해지면 Trust Score 전체가 흔들림 |
| 6 | 완주는 무엇으로 판정하나 | 팀원 전원 동의가 기본, 마감 후 7일 내 미확인 시 시스템 자동 확정 |
| 7 | 강제 상호평가 저항은 어떻게 다루나 | 지금 결정하지 않고 100명 설문 결과로 결정 |
| 8 | 설문에서 뭘 확인해야 하나 | 페인포인트 > 강제평가 거부감 > 대안 대비 사용의향 순으로 우선순위 |
| +1 | 완주 판정 보완 기간은 며칠인가 | 마감일로부터 7일 — 의도적 미확인과 단순 실수를 구분할 최소 기간 |
| +2 | Trust Score 가중치는 어떤 근거로 정하나 | 문서 원안을 그대로 쓰지 않고, 100명 설문에 가중치 문항을 추가해 확정 |
| +3 | 세 시나리오 UX 분기는 언제 정하나 | 공통 기능부터 설계, 시나리오별 차이는 설문 이후에 얹는다 |

---

## 3. 확정된 설계 결정

### 완주 판정 — 전원 동의 + 7일 자동 확정
팀원 전원이 "완료" 확인을 누르면 완주로 기록된다. 마감일로부터 7일 안에 전원 확인이 안 되면 시스템이 자동으로 완주 처리한다.

### 블라인드 상호평가 — 전원 제출 전까지 비공개
완주 처리된 프로젝트에 한해 팀원 전원이 평가에 참여한다. 전원 제출 전까지는 서로의 점수·코멘트를 볼 수 없다. 평가 3회 미만은 "집계 중" 배지로 대체 표기한다.

### Trust Score 가중치 — 잠정값 + 설문 보정
문서 원안(완주율 40%·마감준수 25%·동료평가 25%·최근활동 10%)을 잠정값으로 유지한다. 100명 설문에 가중치 우선순위 문항을 추가해 데이터 기반으로 조정한다.

### 화면·UX 분기 — 공통 기능 우선
공모전·조별과제·동아리 시나리오 구분 없이 팀 스페이스·초대·상호평가 공통 기능부터 만든다. 시나리오별 차이는 설문 결과가 나온 뒤 별도로 추가한다.

## 4. 개발 티켓 로드맵 — 6조각

막힌 게 없는 1번부터 순서대로 진행한다. 하나 끝날 때마다 다음으로 넘어간다. 전체 확인 항목(Given/When/Then)은 [`tickets-itda.md`](tickets-itda.md)에 있다.

```
1. 프로필 등록·조회
   └─ 막고 있는 것: 없음
2. 팀 스페이스 생성 + 초대 + 수락/거절 (마감일 포함)
   └─ 막고 있는 것: 1번
   ├─ 3. 팀 스페이스 목록 화면        (막고 있는 것: 2번)
   └─ 4. 완주 판정 (전원 동의 + 7일 자동 확정)   (막고 있는 것: 2번)
       └─ 5. 블라인드 상호평가        (막고 있는 것: 4번)
           └─ 6. Trust Score 계산 및 프로필 표시  (막고 있는 것: 5번)
```

## 5. 다음 단계 — 대학생 100명 설문

- **문항 수:** 16문항, 5개 섹션 (스크리닝 · 페인포인트 · 상호평가 태도 · 사용의향 · 가중치)
- **예상 소요:** 5~7분
- **확인 우선순위:**
  1. 세 상황 중 진짜 페인포인트가 무엇인가 (Priority A)
  2. 강제 상호평가에 대한 거부감 수준 (Priority B)
  3. 에브리타임·카카오톡 대비 사용 의향(WTU) (Priority C)

설문 결과가 나오면 첫 타겟 시나리오·Trust Score 가중치·UX 분기가 확정된다. 그 전까지는 `tickets-itda.md`의 1번 티켓부터 진행한다.
